# FRPHI — 手机上的 Phira 制谱器 APK

把"打歌"变成"制谱"：导入音乐和背景图，填好曲名/BPM/难度，跟着音乐在设备上敲击，
每一根手指的操作自动转成 Tap / Hold / Flick 音符，一键导出 **.pez** 谱面包，
可直接放进 **Phira** 或 **Re:PhiEdit** 游玩/继续编辑。

## v0.23.0 双押贴图开关 / zip 导入 / 校准修正

**1. 新增「双押贴图」开关（只影响制作界面）**
顶部工具栏「平滑」右边新增按钮，点一下切换：
- **关（默认）**：制作界面双押音符用普通贴图
- **开**：双押音符换成 `*_mh` 贴图

**打歌（Autoplay）界面不受这个开关影响，始终用 mh 贴图。**

**2. 导入支持 .zip**
`pez` 本来就是 zip，所以只认包头（`PK`）不认后缀：`.pez`、`.zip`（改后缀的 pez）、甚至没有后缀都能导入。
不是压缩包时给明确提示「这不是 pez/zip 压缩包（文件头不对）」，不再抛 zip 内部异常。
另外补了三种包结构的测试：标准结构、**文件放在子目录里 + 中文文件名**、**没有 info.txt 且谱面文件名任意**。

**3. 延迟校准修正**
| 问题 | 原来 | 现在 |
|---|---|---|
| 点歪的样本污染结果 | 取 10 次**平均**，一次点在「嗒」上就能把结果拖偏几十毫秒 | 取**中位数**，个别脏数据不影响 |
| 无效点击也计入 | `ACCEPT_WINDOW` 定义了却没用，第一声「滴」之前的点击、点在「嗒」上的点击都算 | 只接受「滴」前 300ms ~ 后 600ms 内的点击，且第一声「滴」之前不记 |
| 负数结果被丢弃 | `MainActivity` 里 `if (v >= 0)`，提前点出来的负延迟直接被扔掉（等于没校准） | 负数照常填入 |
| 校准页音符比声音早到线 | `currentPosition` 比"耳朵听到"超前一个输出延迟（蓝牙耳机 150~300ms），音符先落线、声音后到 | 用已测出的偏移把落线时刻补回来，几次点击后音符与「滴」同步 |
| 结果不够透明 | 只显示一个数 | 显示中位数 + 本次范围，一眼能看出是否点得太散 |

匹配逻辑抽到 `CalibMath`（纯函数），7 个单测覆盖：点正/点晚/点在「嗒」上/第一声滴之前/太晚/中位数抗离群/空列表。

> 说明：导出时 `音符时间 -= 延迟` 这个换算没变（校准测出来的就是"这个设备上音符会晚多少"）。
> 制作界面里音符相对音乐只差玩家自己的反应误差（几十毫秒），这是"延迟"本身无法分离的部分，
> 所以预览不做额外偏移，避免把设备延迟重复算两次。

## v0.22.0 真撤销 / 返回确认 / 双押贴图

**1. 撤销变成真的多步撤销**
原来是"删掉最后一个音符"。现在每次触摸（按下→抬起）算一个撤销步，最多记 200 步，可连续撤销：

| 能撤销的操作 | 说明 |
|---|---|
| 放置音符 | 点按 / 长按连铺 / 第四次长条 |
| 拖动移动 | 单个拖动、框选后整组拖动（整组一步） |
| 删除 | 点红框删除全部、框选删除 |
| 判定线 | 拖动平移、旋转 |
| 关键帧 | 打帧、删帧（姿态一起回退） |

实现（`Undo.kt` + `RecordView`）：每步只记**增量**（追加了哪个音符 / 在哪个下标删了哪个 / 哪个下标被改成什么旧值 / 关键帧与姿态的旧值），
撤销时把操作列表**逆序重放**。上万音符的谱面也只占几十 KB，不整份快照。
撤销后清空选中集、重建时间索引，并提示"还可撤销 N 步"；打歌中禁止撤销。

> 这里踩过两个坑，都是随机对拍测试（`UndoTest`）抓出来的：① 一次删多个时按下标升序插回会错位，必须按删除的逆序；
> ② 同一步里"删 + 改"混在一起时，下标增量模型必然错位 —— 所以最终改成有序操作列表逆序重放。

**2. 返回改为"是否保存这次改动"**
`返回键` 和顶部`退出`都弹：**保存**（写入项目草稿并退出）/ **不保存**（丢弃本次改动）/ **取消**。
导出仍然走右上角「导出 .pez」，不再和返回键混在一起。

**3. 双押改用 `*_mh` 贴图，去掉黄框**
`assets/notes/` 里本来就有 `click_mh / drag_mh / flick_mh / hold_mh`（同尺寸音符主体 + 一圈金色光晕）。
原来只在 Autoplay 里用，还在外面套了个黄框。现在：
- 四类音符双押时都直接换成对应 `*_mh` 贴图，**不再画黄框**（`drawDoubleGlow` 已删除）
- 贴图宽度按"mh 图 / 普通图"的实际比例放大（≈1.15，与 Phira 的
  `note_style_mh.click.width / note_style.click.width` 一致），保证音符主体大小不变、只多出光晕
- 编辑界面里也按双押显示 mh 贴图（原来只有打歌时才换）

## v0.21.0 性能优化（导入大谱面不再卡）

大谱面卡在"每帧重复计算"，不是解压/解析 pez。逐项修掉，并加了 JVM 基准（`app/src/test` 里会打印）：

| 问题 | 原来 | 现在 |
|---|---|---|
| 双押检测 `doubleHintIdx` | 未判定音符两两比较 **O(n²)**，每帧跑一次 | 按时间排序后滑窗 + 只处理屏幕附近的时间段 |
| 判定线姿态 `linePoseAt` | 每次调用 `sortedBy{}` 新建列表并排序；每个音符要调 2 次 | 关键帧排序缓存 + 二分，每帧只算 1 次并传给绘制 |
| 音符绘制循环 | `withIndex()` 每帧分配 n 个对象；每音符重算姿态 | `for (i in notes.indices)`，姿态/中心/旋转作为参数传入 |
| 草稿序列化 | org.json 逐条建对象（UI 线程） | `DraftCodec` 逐行文本，导入时在后台线程写 |
| 草稿解析 | onCreate 同步 org.json 解析 | 后台解析 + 应用后再并回"载入期间用户放的音符" |
| 背景图 | 全尺寸解码（可能几十 MB），每帧缩放并 new RectF | 按屏幕尺寸 `inSampleSize` 降采样，RectF 复用 |
| 框选 / Autoplay 命中 | 每个音符都算一次姿态（带排序） | 姿态移到循环外 |
| 点选音符 `findNoteAt` | 每音符 `noteScreenPos`（2 个数组 + 2 次排序） | 预先算好中心/旋转，纯算术 |

基准（JVM，`AlgosTest` / `DraftCodecTest` 打印）：

```
双押检测  1000 音符  8.2ms → 0.043ms   (×190)
双押检测  3000 音符 40.5ms → 0.169ms   (×239)
双押检测 10000 音符 468.8ms → 0.459ms  (×1021)
判定线插值 6000 次/帧 3.06ms → 0.42ms  (×7)
草稿编码 1 万音符 25.5ms → 5.0ms (×5)，解码 30.9ms → 16.1ms，体积 574KB → 258KB
```

> 关于"按可视区裁剪音符"：评估后没做。姿态计算提到循环外以后，屏幕外音符只剩两次乘法 + 一次比较
> （1 万音符约 0.1~0.3ms/帧）；而 `selectedSet`/`judgedIdx`/`holdFxList` 都按下标引用音符，
> 对 `notes` 重排会牵连一片；长条 Hold 又可能"起点在屏外、身体还在屏内"，按起点裁剪会漏画。
> 收益小而风险大，所以先不做。

## v0.20.1 标签逻辑修复（导入不再清空、删标签不再误删）

**1. 导入谱面会清空所有标签**
`applyImported` 里是 `tabs.clear(); tabs.add(t)`（早期"单项目模式"遗留）。现在导入结果
作为**新标签**加入，已有标签一个都不动，导入完自动切到新标签。

**2. 删掉一个标签会把别的标签也删了**
`deleteTab` 的顺序反了：先 `tabs.removeAt(i)` 再 `saveCurrent()`。`saveCurrent()` 写的是
**界面上还没刷新的输入框**（也就是被删标签的内容），而此时 `tabs[current]` 已经指向
"顶上来"的那个标签 —— 等于把 A 的内容覆盖到 B 上，看起来就是"删一个把另一个删了"。
现在顺序固定为：`saveCurrent()` → `removeAt` → 算新下标 → `restore` → `saveTabs` → `renderTabs` → 清理文件，
下标计算抽到 `TabOps.afterDelete()` 并有穷举单测。

**3. 顺带修掉的三个同源隐患**
- **id 为空/重复会让多个标签共用同一份文件**：草稿是 `drafts/<id>.json`、素材是 `imported/<id>/`。
  旧数据里 id 为空时，`File(filesDir, "imported/")` 就是整个素材目录，删一个标签会把
  **所有**导入素材清空。现在 `loadTabs` 会给空/重复 id 补新的唯一 id，`purgeTabFiles` 只放行
  UUID 形态的 id（`TabOps.isSafeId`）。
- **选素材会写错标签**：原来结果回来时按 `current` 落位，界面被系统回收重建后 `current` 会变，
  素材就写到别的项目上。现在记录发起选择时的标签 id，按 id 落位。
- **离开界面不落盘**：新增 `onPause` 时 `saveCurrent() + saveTabs()`，避免被系统回收丢改动。

**4. 小改善**：标签名改完立刻刷新标签栏（不用切一下才变）。

测试：`app/src/test/java/com/piezmaker/TabOpsTest.kt`（下标穷举 + id 白名单）。

## v0.19.0 导入修复（从 Phira 下载的 pez 现在能完整读进来）

之前导入只读了 `chart.json` 里的音符，其余全丢。现在 `PezImporter` 按 Phira
`prpr/src/parse/rpe.rs` 的规则完整解析，并抽取包内素材：

| 项目 | 之前 | 现在 |
|---|---|---|
| 音频 | 不读 | 从包里抽出 `Song` 指向的音频（找不到按扩展名兜底），存到应用私有目录并设为项目音频 |
| 背景图片 | 不读 | 抽出 `Picture` 指向的图，设为项目背景（编辑界面直接显示） |
| 流速 | 写死 1.0 | 读 `speedEvents`（恒定值直接取；有动画时取开头值并提示） |
| 判定线位置 | 写死居中 | 读 `moveYEvents` → 设置页「判定线位置」百分比（`pct = 50 - moveY/9`，RPE moveY 向上为正） |
| 判定线 | 只认一条、姿态丢失 | 读 `moveXEvents` / `rotateEvents` → 全局偏移与旋转；随时间变化的事件转成**关键帧**（可按时间回放）；多条判定线自动合并到音符最多的那条，其它线的横向偏移换算进音符位置 |
| 横线数 | 猜第一个音符分母 | 取所有时间分母的最小公倍数（谱师原本的量化格），如全 1/4 → 4 |
| 竖线数 | 永远是 8 | 由 `positionX` 反推（能精确表示所有位置的最少格数） |
| 曲目信息 | 字段名错（读 `title`/`artist`，RPE 里是 `name`/`composer`） | `META` 优先、`info.txt` 兜底（兼容 GBK 编码的 `info.txt`） |
| 时间 | 只按首个 BPM 换算 | 支持 `BPMList` 多 BPM 分段换算，并叠加 `META.offset`（Phira：`谱面时间 = 音乐时间 - offset`） |
| 其它 | — | 跳过 `isFake` 假音符；`extra.json` 不会被误当谱面；导入在后台线程，素材不整包进内存；删标签时清掉该项目素材 |

同时修掉两个导出问题：判定线关键帧之前没写进 `chart.json`（`export` 漏传参数），
关键帧的 Y 缩放/方向也错了（应用 450 而不是 675，且要取反）；拖动判定线但没打关键帧时
偏移会丢失（现在导出用当前姿态）。

> 说明：本项目是**单判定线、单 BPM、恒定流速**的录制器，多线/多 BPM/流速动画的谱面
> 只能近似（导入时会弹「导入提示」逐条说明做了哪些近似）。

## 核心流程

1. **设置页**（默认横屏）：选音频 + 选背景图，填曲名 / 曲师 / 谱师 / 难度 / BPM / **流速** / **判定线位置** / 横线数 / 竖线数
   - **横线数**＝时间量化精度：每拍分成几格，音符时刻会吸附到格点上（如 4 = 每拍 4 格 = 16 分音符）
   - **竖线数**＝位置量化精度：判定线左右分成几格，音符左右位置会吸附到格点上（如 8）
   - **流速**＝音符下落倍率（默认 1.0），写入判定线 speedEvents
   - **判定线位置**＝判定线在屏幕上的纵向百分比（0~100，默认 60），写入 moveYEvents；**注意 RPE 的 moveY 向上为正**，所以 40%（靠上）=+90、60%（靠下）=-90。录制界面判定线同步画在该位置，所见即所得
   - **延迟**＝自动校准或手填（ms）。点「延迟校准」后听到「嘀」就点屏幕，共 10 次，取中位数作为建议值；导出时音符时间统一减掉这个延迟
2. 点「开始录制」→ 音乐播放，进入音游界面（背景图 + 判定线 + 网格）
3. **跟着音乐敲击**（支持多指同时）：
   - 快速点按 → `Tap`
   - 长按（≥280ms）→ `Hold`
   - 按住左右滑动超过 1 个竖线格 → `Hold`（滑动 hold）
   - 上下滑动 / 轻微左右滑动（不超过 1 个竖线格）→ `Flick`
4. 「导出 .pez」→ 系统保存对话框选位置，得到可在 Phira / RPE 中打开的谱面包

## 实时反馈

录制界面每帧持续刷新：按下的手指**立刻**在判定线对应格点渲染音符预览（点按为青色光圈，按住超过阈值后长出橙色 hold 条），松手即落成正式音符，不会出现"按了没反应"。

## 素材兼容（v0.2.0 修复）

- **图片**：任何格式（jpg/webp/gif/bmp 等）一律**解码重编码为真 PNG** 再打包，
  从根本上杜绝「内容与 .png 头不匹配」——即使系统给的文件名是 `image_xxx.png` 而实际字节是 JPEG
- **音频**：按**魔数嗅探**真实格式命名（OggS→ogg、RIFF/WAVE→wav、ID3/FFFB→mp3、ftyp→m4a、fLaC→flac），
  不再轻信文件名后缀

## 关于"横线竖线"

按你的定义：**竖线垂直于判定线方向，限制音符左右偏移**（位置量化）；
**横线是时间轴量化**（每拍分几格）。你要求"横线间距随 BPM 变化"——已按你的要求**不做**，横线为固定网格。

## 导出的 PEZ 结构（格式已与 Phira 源码交叉验证）

```
chart.json        # RPEJSON：META + BPMList + 单条判定线 judgeLineList
info.txt          # RPE 标准：# 开头 + Name/Song/Picture/Chart/Level/Composer/Charter
music.*           # 音频原样打包
bg.*              # 背景图原样打包
```

- RPE note type：`1=Tap 2=Hold 3=Flick 4=Drag`（与 Phira `prpr/src/parse/rpe.rs` 一致）
- 时间单位 beat：`beat = 秒 × bpm / 60`，量化到 `1/横线数` 拍，Triple 表示 `[i,n,d] = i + n/d`
- 延迟校正：导出前 `note.startMs -= delayMs`（把因设备延迟而记晚的音符拉回）
- 坐标：positionX 范围 `[-675, 675]`（解析端除以 675 归一化），量化到 `1/竖线数` 格
- 判定线：单条，`Texture: "line.png"`（Phira 内置 Normal 线，无需贴图资源）
